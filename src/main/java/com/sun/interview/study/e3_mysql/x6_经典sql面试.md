# count(1) count(id) count(*) 区别

|函数|含义|统计范围|性能|使用场景|
|--|--|--|--|--|
|`COUNT(*)`|统计结果集中的所有记录数，对表的行进行计数，不考虑具体列的值|所有行，包括列值为`NULL`的行|在InnoDB存储引擎中，会利用索引快速统计行数，通常性能较好|需要统计表中所有记录数量，不关心列值是否为`NULL`的情况|
|`COUNT(1)`|功能与`COUNT(*)`基本一致，将每行都视为一个`1`，统计`1`的数量|所有行，包括列值为`NULL`的行|与`COUNT(*)`性能相近，在MySQL中二者处理方式基本相同，差异极小|可作为`COUNT(*)`的替代写法，但一般优先使用`COUNT(*)`|
|`COUNT(id)`|统计指定列`id`不为`NULL`的记录数量|仅统计指定列值不为`NULL`的行|若`id`列有索引，可利用索引快速统计；若没有索引，则需全表扫描，性能相对较差|只需要统计某一列不为`NULL`的记录数量的情况，如统计某列有值的记录数|
# union&union all

|比较项|UNION|UNION ALL|
| ---- | ---- | ---- |
|区别|会对多个`SELECT`语句的结果集进行合并，并自动去除重复的行。执行时需要额外的排序和比较操作来实现去重|直接将多个`SELECT`语句的结果集合并在一起，不会对结果集进行去重操作，执行过程相对简单|
|使用场景|当需要合并多个结果集，并且不希望结果集中存在重复的行时使用。例如，从不同的数据源获取用户信息，需要确保最终结果中的用户信息唯一|当确定多个结果集之间不存在重复行，或者不关心结果集中是否有重复行时使用，能显著提高查询性能。例如，按时间范围拆分的销售数据进行合并统计，各时间段数据无重复|


# uuid和bigint作为主键对比
|对比项|UUID|Bigint|
|--|--|--|
|数据类型特点|UUID是128位的通用唯一识别码，通常以32位十六进制数字表示，中间用连字符分隔，表现形式为`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`。它具有全球唯一性，理论上不会出现重复。|Bigint是8字节（64位）的有符号整数类型，取值范围为`-9223372036854775808`到`9223372036854775807`。|
|优点|**唯一性高**：在全球范围内几乎不可能出现重复，即使在分布式系统中，不同节点生成的UUID也能保证唯一性，适用于数据需要在多个系统间合并或共享的场景。<br>**安全性高**：UUID的随机性和无规律性，使得通过猜测或枚举的方式获取数据变得极为困难，在一定程度上增强了数据的安全性。<br>**数据迁移方便**：与具体的数据库环境和服务器配置无关，在不同数据库或服务器之间进行数据迁移时，不需要担心主键冲突问题。|**占用空间小**：只需要8个字节来存储，相比UUID占用的空间少很多，在存储大量数据时，可以节省大量的存储空间。<br>**查询效率高**：作为整数类型，在数据库中进行索引和查询操作时，比UUID的字符串类型效率更高，尤其是在进行范围查询、排序等操作时表现更优。<br>**自增特性**：通常可以设置为自增长类型，数据库会自动按照顺序生成唯一的数值，无需应用程序额外处理，保证了数据的顺序性和连续性，对于一些需要按照插入顺序进行查询或处理的场景非常方便。|
|缺点|**存储空间大**：通常以字符串形式存储，需要占用更多的存储空间，一般为36个字符（包括连字符），如果存储大量数据，会增加数据库的存储成本。<br>**查询性能相对低**：由于是字符串类型，在进行查询、索引和排序操作时，数据库需要进行更多的计算和比较，性能相对整数类型会低一些。<br>**可读性差**：UUID是一个无意义的字符串，不具有直观的语义，对于开发人员和用户来说，难以通过UUID直接了解数据的相关信息。|**唯一性依赖系统**：在单个数据库实例中容易保证唯一性，但在分布式系统中，如果多个节点同时生成数据，可能会出现主键冲突的情况，需要额外的机制来保证唯一性。<br>**存在溢出风险**：虽然取值范围很大，但在某些极端情况下，如果数据增长过快，可能会出现数据溢出的问题，导致主键值重复或错误。<br>**数据迁移复杂**：在不同数据库或服务器之间进行数据迁移时，如果目标系统的主键设置与原系统不同，可能会导致主键冲突，需要进行额外的处理来保证数据的一致性。|
|适用场景|**分布式系统**：在分布式数据库、微服务架构等环境中，不同节点生成的数据需要保证唯一性，UUID是一个很好的选择，如多个服务器之间的数据同步场景。<br>**数据安全要求高**：对于一些对数据安全性要求较高的场景，如用户认证、加密数据存储等，UUID的随机性和唯一性可以增加数据的保密性和完整性。<br>**数据共享与交换**：当数据需要在不同的系统或组织之间进行共享和交换时，UUID可以确保在不同的环境中数据的唯一性，避免主键冲突。|**传统关系型数据库**：在大多数传统的关系型数据库应用中，如果数据量不是特别巨大，且不需要考虑分布式环境下的唯一性问题，Bigint作为主键是一个性能和空间上都比较平衡的选择，如一般的企业级应用数据库。<br>**顺序性要求高**：对于一些需要按照顺序插入和查询数据的场景，如日志记录、订单编号等，Bigint的自增特性可以很好地满足需求，方便进行数据的排序和分页操作。<br>**数据仓库**：在数据仓库环境中，通常会对大量的数据进行聚合和分析，Bigint作为主键可以提高查询和分组操作的效率，减少存储空间的占用。|


# varchar(30)超出长度会怎么处理？

|模式|对`varchar(30)`超出长度的处理|操作结果|数据影响|提示信息|
| ---- | ---- | ---- | ---- | ---- |
|严格模式|阻止插入或更新操作|操作失败，数据不会被插入或更新到表中|无数据写入，保证了数据的完整性，避免了因截断数据导致的信息丢失|抛出错误，通常会提示数据截断相关的错误信息，如`Data too long for column 'column_name' at row 1`  |
|非严格模式|自动截断超出部分的数据|操作成功，数据会被插入或更新到表中，但只保留前30个字符|部分数据丢失，可能会影响业务逻辑和数据的准确性|产生警告信息，可以通过`SHOW WARNINGS`查看，提示数据被截断  |

### MySQL 默认模式情况
在不同的 MySQL 版本中，默认的 SQL 模式有所不同。早期的 MySQL 版本默认是非严格模式，但从 MySQL 5.7 开始，默认启用了严格模式。

# 严格模式和非严格模式优缺点对比

|对比项|严格模式|非严格模式|
| ---- | ---- | ---- |
|优点|1. **保证数据完整性**：严格检查插入和更新的数据，确保数据符合表结构定义，避免不合法数据进入数据库。例如，对于有长度限制的字段，不会出现数据截断问题；对于要求非空的字段，不会插入 `NULL` 值。<br>2. **提前发现问题**：在开发和测试阶段能快速定位数据输入和处理中的错误，避免问题遗留到生产环境。<br>3. **提高代码质量**：促使开发者编写更严谨的代码，注重数据验证和处理逻辑。|1. **提高兼容性**：允许插入一些不符合严格规范的数据，对于旧的应用程序或脚本，无需大量修改即可继续运行，降低系统升级和迁移成本。<br>2. **简化开发流程**：开发者在处理数据时可减少数据验证步骤，在对数据质量要求不高的场景下能快速实现功能。|
|缺点|1. **增加开发和测试成本**：开发者需花费更多时间处理数据验证和错误处理逻辑，增加开发难度和工作量。<br>2. **兼容性问题**：可能导致旧应用程序或第三方脚本出现兼容性问题，需要进行修改才能正常运行。|1. **数据质量下降**：可能会有大量不合法或不完整的数据进入数据库，影响数据质量和可用性，给后续数据分析等工作带来困难。<br>2. **增加后期维护成本**：随着业务发展和数据量增加，处理低质量数据的难度增大，需花费更多时间和精力清理和修复数据。|

# 慢sql定位排查

* 1.修改配置记录执行时间超过规定值的sql到指定文件
* 2.分析慢sql文件
  * mysql自带工具 mysqldumpslow 可对日志文件进行统计和排序。
    * 例如，找出执行时间最长的前 10 条慢 SQL：mysqldumpslow -s t -t 10 /var/log/mysql/mysql-slow.log
  * 第三方工具 
    *  可以使用 `pt-query-digest` 等第三方工具对慢查询日志进行更详细的分析，它能生成详细的报告，包括 SQL 执行次数、平均执行时间、锁等待时间等信息。
* 3.在从库模拟执行 分析sql执行计划  
  * 分析索引是否合规，生效
  * 分析业务逻辑是否合理，是否存在大事务操作等

# 复杂sql练习-1 查询每个班级成绩前五的学生
```sql
SELECT
    s1.student_id,
    s1.class_id,
    s1.score
FROM
    student_scores s1
        LEFT JOIN
    student_scores s2
    ON
        s1.class_id = s2.class_id AND s1.score < s2.score
GROUP BY
    s1.student_id,
    s1.class_id,
    s1.score
HAVING
    COUNT(s2.student_id) < 5
ORDER BY
    s1.class_id,
    s1.score DESC;

```
