### MySQL MVCC 机制介绍
MVCC（Multi-Version Concurrency Control，多版本并发控制）是 MySQL InnoDB 存储引擎为了提高并发性能而实现的一种并发控制机制。它允许事务在不同的时间点看到数据的不同版本，从而在保证数据一致性的前提下，减少了锁的竞争，提高了并发读写的性能。MVCC 主要依赖于隐藏列、Undo Log 和 Read View 来实现。
- **隐藏列**：InnoDB 为表的每一行记录添加了三个隐藏列。`DB_TRX_ID` 记录最后一次修改该行的事务 ID；`DB_ROLL_PTR` 是回滚指针，指向该行的上一个版本；`DB_ROW_ID` 是行 ID，若表中没有主键和唯一非空索引时会自动生成。
- **Undo Log**：用于记录数据的旧版本。当一个事务修改数据时，会将旧数据的版本信息记录到 Undo Log 中，通过回滚指针可以找到这些旧版本。
- **Read View**：读视图，用于判断某个版本的数据对当前事务是否可见。

### 生成快照的过程
1. **事务开始**：当一个事务开始执行时，并不会立即生成快照。
2. **查询触发**：当事务执行 `SELECT` 语句时，会触发快照的生成。具体步骤如下：
    - **生成 Read View**：事务会创建一个 Read View，Read View 中包含了当前活跃事务的列表、最小活跃事务 ID 和最大活跃事务 ID 等信息。
    - **遍历数据行**：存储引擎会遍历查询涉及的所有数据行，对于每一行数据，根据其 `DB_TRX_ID` 和 `DB_ROLL_PTR` 信息，结合 Read View 来判断该行数据的可见版本。
    - **确定可见版本**：
        - 如果数据的 `DB_TRX_ID` 小于 Read View 中的最小活跃事务 ID，说明该数据在当前事务开始之前就已经被提交，对当前事务可见。
        - 如果数据的 `DB_TRX_ID` 大于等于 Read View 中的最大活跃事务 ID，说明该数据是在当前事务开始之后才产生的，对当前事务不可见。
        - 如果数据的 `DB_TRX_ID` 在 Read View 的最小活跃事务 ID 和最大活跃事务 ID 之间，需要进一步判断该事务 ID 是否在 Read View 的活跃事务列表中。如果不在，说明该事务已经提交，数据对当前事务可见；如果在，说明该事务还未提交，数据对当前事务不可见。如果当前版本的数据不可见，会通过 `DB_ROLL_PTR` 到 Undo Log 中查找上一个可见版本的数据。

### 当前读是什么及怎么实现
#### 当前读的定义
当前读是指读取数据的最新版本，而不是基于 MVCC 的快照版本。它会读取其他事务已经提交的最新数据，并且会对读取的数据行加锁，以保证读取到的数据是最新的。

#### 实现方式
在 MySQL 中，以下语句属于当前读操作：
- `SELECT ... FOR UPDATE`：对查询结果集中的每一行数据加上排他锁，其他事务无法对这些行进行修改或删除。
```sql
SELECT * FROM table_name WHERE condition FOR UPDATE;
```
- `SELECT ... LOCK IN SHARE MODE`：对查询结果集中的每一行数据加上共享锁，其他事务可以读取这些行，但不能对其进行修改，直到当前事务释放锁。
```sql
SELECT * FROM table_name WHERE condition LOCK IN SHARE MODE;
```
- `INSERT`、`UPDATE`、`DELETE` 语句：这些语句在执行时会对涉及的数据行进行加锁，读取最新的数据版本并进行相应的修改。

### 当前读存在的问题
- **锁竞争**：当前读会对数据行加锁，可能会导致锁竞争问题。当多个事务同时对同一数据行进行当前读操作时，会相互阻塞，降低并发性能。
- **死锁风险**：由于当前读会加锁，如果事务之间的加锁顺序不一致，可能会导致死锁的发生。例如，事务 A 对记录 1 加锁，然后尝试对记录 2 加锁；同时事务 B 对记录 2 加锁，然后尝试对记录 1 加锁，就可能会出现死锁。

### 可重复读（RR）隔离级别下如何解决幻读
在可重复读隔离级别下，InnoDB 使用 MVCC 结合间隙锁（Gap Lock）和临键锁（Next-Key Lock）来解决幻读问题。
- **MVCC 部分**：在可重复读隔离级别下，事务在开始时会创建一个 Read View，后续的查询都会根据这个 Read View 来判断数据的可见性。同一个事务中，多次执行相同的查询语句时，看到的数据版本是一致的，避免了因为其他事务修改数据而导致的幻读问题。
- **间隙锁和临键锁**：
    - **间隙锁**：当一个事务执行 `SELECT ... FOR UPDATE`、`SELECT ... LOCK IN SHARE MODE` 等加锁查询语句，或者执行插入、更新、删除操作时，InnoDB 会在查询条件的范围上加间隙锁。间隙锁锁定的是索引记录之间的间隙，防止其他事务在这些间隙中插入新的记录。
    - **临键锁**：临键锁是间隙锁和记录锁的组合，它不仅锁定索引记录本身，还锁定该记录前面的间隙。例如，对于记录 `(3, 'b')`，临键锁会锁定 `(1, 3]` 这个范围，既防止其他事务修改该记录，也防止在该记录前面的间隙插入新记录。

通过间隙锁和临键锁，InnoDB 可以防止其他事务在当前事务的查询范围内插入新的记录，从而解决了幻读问题。 



# 锁

MySQL 中的锁可以从多个维度进行分类，下面将详细介绍各类锁的特点、使用方法和应用场景。

### 按锁粒度分类

#### 表级锁
- **特点**：对整张表加锁，实现简单，加锁和解锁速度快，但并发度低，同一时刻只能有一个事务对表进行读写操作。
- **使用方法**
    - **手动加共享锁**：
```sql
LOCK TABLES table_name READ;
-- 执行读操作
UNLOCK TABLES;
```
    - **手动加排他锁**：
```sql
LOCK TABLES table_name WRITE;
-- 执行写操作
UNLOCK TABLES;
```
- **应用场景**：适合对表进行批量操作或者并发访问较低的场景。例如执行 `ALTER TABLE` 等 DDL 操作时，为避免其他事务干扰，可使用表级锁；数据量小且并发不高的系统中，使用表级锁能简化锁管理。

#### 行级锁
- **特点**：仅对操作涉及的行加锁，并发度高，但加锁和解锁开销大。InnoDB 存储引擎支持行级锁。
- **使用方法**
    - **共享锁（读锁）**：
```sql
SELECT * FROM table_name WHERE condition LOCK IN SHARE MODE;
```
    - **排他锁（写锁）**：
```sql
SELECT * FROM table_name WHERE condition FOR UPDATE;
```
- **应用场景**：在高并发的 OLTP（联机事务处理）系统中广泛应用。比如电商系统的库存管理、订单处理，银行系统的账户余额更新等，可对单条记录频繁操作，减少锁冲突，提高并发性能。

#### 页级锁
- **特点**：锁定粒度介于表级锁和行级锁之间，对数据页加锁，并发度和锁开销也处于两者之间，实现相对复杂。
- **使用方法**：在 MySQL 中一般较少手动使用页级锁，主要由存储引擎（如 BDB 存储引擎）内部管理。
- **应用场景**：在一些特殊的存储引擎和特定业务场景下使用，不过由于 InnoDB 行级锁已能满足多数需求，页级锁应用相对较少。

### 按锁类型分类

#### 共享锁（读锁）
- **特点**：允许多个事务同时获取同一数据的共享锁进行读取操作，互不冲突，但不允许获取排他锁。
- **使用方法**：
```sql
SELECT * FROM table_name WHERE condition LOCK IN SHARE MODE;
```
- **应用场景**：适用于多个事务需同时读取同一数据的场景，以提高并发读取效率。例如电商系统中多个用户同时查看商品信息，可同时获取共享锁，不会相互阻塞。

#### 排他锁（写锁）
- **特点**：一个事务获取排他锁后，其他事务无法获取该数据的任何锁，直到排他锁释放。
- **使用方法**：
```sql
SELECT * FROM table_name WHERE condition FOR UPDATE;
```
- **应用场景**：用于数据修改操作，如 `INSERT`、`UPDATE`、`DELETE` 语句。像银行转账系统，对账户余额更新时需获取排他锁，保证数据一致性。

### 按使用方式分类

#### 显式锁
- **特点**：由用户通过 SQL 语句手动添加。
- **使用方法**：上述提到的 `LOCK TABLES`、`SELECT ... LOCK IN SHARE MODE`、`SELECT ... FOR UPDATE` 等都是显式锁的使用方式。
- **应用场景**：当需要对数据进行特殊并发控制，或在特定业务逻辑中明确需要加锁时使用。例如实现分布式锁或对关键业务数据严格并发控制。

#### 隐式锁
- **特点**：由数据库自动添加，用户无需手动干预。
- **使用方法**：执行 `INSERT`、`UPDATE`、`DELETE` 等操作时，数据库自动对涉及的数据行添加排他锁。
- **应用场景**：适用于大多数常规数据库操作，数据库根据操作类型和隔离级别自动加锁，保证数据一致性和并发性能，一般业务开发中多数情况使用隐式锁即可。

### 其他特殊锁

#### 意向锁
- **特点**：是一种表级别的锁，用于表明某个事务正在对表中的某一行或多行进行某种类型的锁定。分为意向共享锁（IS）和意向排他锁（IX）。
- **使用方法**：意向锁由数据库自动管理，用户无需手动操作。当事务对行加共享锁前，数据库会自动在表上添加意向共享锁；加排他锁前，会自动添加意向排他锁。
- **应用场景**：用于协调表级锁和行级锁之间的关系，提高加锁效率。例如，当要对表加表级排他锁时，可先检查是否存在意向锁，若有则表明有事务正在对表中的行进行锁定，可避免直接尝试加锁导致的大量行级锁检查。

#### 间隙锁
- **特点**：锁定索引记录之间的间隙，防止其他事务在间隙中插入新记录，避免幻读问题。
- **使用方法**：在可重复读隔离级别下，使用 `SELECT ... FOR UPDATE` 等语句可能会触发间隙锁。例如：
```sql
SELECT * FROM table_name WHERE column_name BETWEEN 10 AND 20 FOR UPDATE;
```
- **应用场景**：主要用于可重复读隔离级别下防止幻读。例如在订单系统中，防止在查询订单范围时，有新的符合条件的订单插入。

#### 临键锁
- **特点**：是间隙锁和记录锁的组合，既锁定记录本身，也锁定记录前面的间隙。
- **使用方法**：同样在可重复读隔离级别下，使用 `SELECT ... FOR UPDATE` 等语句可能会触发临键锁。
- **应用场景**：用于可重复读隔离级别下防止幻读和保证数据一致性。在一些对数据一致性要求较高的业务场景中，如金融交易系统，可避免数据插入和修改带来的不一致问题。
