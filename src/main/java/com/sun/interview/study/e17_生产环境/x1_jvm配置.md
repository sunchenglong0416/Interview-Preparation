# CMS 垃圾回收器在 JDK 9 中已被标记为废弃，在 JDK 14 中被移除。

# jdk 17 为例

- **初始堆大小（-Xms）**：默认情况下，初始堆大小为物理内存的 1/64。对于 8GB 物理内存的机器，初始堆大小约为 8GB / 64 = 128MB 。不过，初始堆大小有下限限制，一般不会低于 2MB 或 4MB （具体取决于操作系统和 JVM 实现）。
- **最大堆大小（-Xmx）**：默认最大堆大小为物理内存的 1/4。对于 8GB 物理内存的机器，最大堆大小约为 8GB / 4 = 2GB。

- 直接设置-Xms和-Xmx参数大小一样大 避免动态申请内存

生代占堆内存的 1/3，老年代占 2/3
- **新生代与老年代比例（-XX:NewRatio）**：默认比例为 2，即老年代是新生代的 2 倍，意味着新生代占堆内存的 1/3，老年代占 2/3。若最大堆大小为 2GB，那么新生代约为 682MB（2GB / 3），老年代约为 1365MB（2GB * 2 / 3）。
- **新生代内部比例（-XX:SurvivorRatio）**：默认情况下，新生代由一个 Eden 区和两个 Survivor 区组成，`SurvivorRatio` 的默认值为 8，即 Eden 区与一个 Survivor 区的比例为 8:1。所以，Eden 区约占新生代的 8/10，两个 Survivor 区各占 1/10。


### 减少垃圾回收时的性能开销
- **避免堆大小动态调整**：当 `-Xms` 和 `-Xmx` 不一致时，JVM 会根据应用程序的内存使用情况动态调整堆的大小。堆大小的动态调整涉及到内存的分配和释放操作，这些操作会消耗系统资源，并且可能导致应用程序的性能波动。例如，当堆内存不足时，JVM 会尝试扩大堆的大小，这可能需要向操作系统请求更多的内存，这个过程可能会比较耗时。而将 `-Xms` 和 `-Xmx` 设置为相同的值，堆的大小在应用程序启动时就固定下来，避免了堆大小动态调整带来的性能开销。
- **稳定垃圾回收行为**：堆大小的稳定有助于垃圾回收器更稳定地工作。垃圾回收器在进行垃圾回收时，需要根据堆的大小和内存使用情况来选择合适的回收算法和策略。如果堆的大小不断变化，垃圾回收器需要不断地调整自己的行为，这可能会导致垃圾回收的效率降低。而固定堆大小可以让垃圾回收器在一个相对稳定的环境中工作，提高垃圾回收的效率和可预测性。

### 提高应用程序的响应速度
- **减少内存分配延迟**：在应用程序运行过程中，对象的创建需要分配内存。如果堆的大小不稳定，当堆内存不足时，JVM 需要进行堆的扩容操作，这会导致对象分配内存的延迟增加。而将 `-Xms` 和 `-Xmx` 设置为相同的值，堆的大小始终保持不变，对象分配内存的过程更加稳定，减少了内存分配的延迟，从而提高了应用程序的响应速度。
- **避免 Full GC 频繁触发**：堆大小的动态调整可能会导致频繁的 Full GC（全量垃圾回收）。当堆内存不足时，JVM 可能会触发 Full GC 来回收更多的内存，Full GC 会导致应用程序的停顿时间较长，影响应用程序的响应速度。而固定堆大小可以减少这种情况的发生，降低 Full GC 的触发频率，提高应用程序的响应性能。

### 便于性能调优和监控
- **简化调优过程**：将 `-Xms` 和 `-Xmx` 设置为相同的值，减少了一个需要调整的参数，简化了 JVM 性能调优的过程。开发者可以更专注于其他参数的调整，如新生代和老年代的比例、垃圾回收器的选择等，提高调优的效率。
- **更准确的性能监控**：在性能监控方面，固定堆大小可以让开发者更准确地了解应用程序的内存使用情况。因为堆的大小始终保持不变，内存使用的变化更加直观，便于开发者分析应用程序的内存使用模式和性能瓶颈。
