# 短时间内 匀速大量写入key 且未设置合理过期时间
# 处理方式 
在 Redis 中，如果内存被打满（即达到 `maxmemory` 配置的限制），Redis 会根据配置的淘汰策略来决定是否允许继续写入数据以及如何处理已有的数据。以下是几种常见情况：

### 1. **maxmemory 淘汰策略**
Redis 提供了多种 `maxmemory-policy` 配置选项，用于控制当内存达到上限时的行为：

- **noeviction**（默认策略）  
  当内存达到上限时，所有写入操作都会返回错误（客户端会收到 `OOM` 错误），但读取操作仍然可以正常进行。

- **allkeys-lru / volatile-lru**  
  根据最近最少使用（LRU）算法淘汰键。`allkeys-lru` 会对所有键生效，而 `volatile-lru` 只对设置了过期时间的键生效。

- **allkeys-lfu / volatile-lfu**  
  根据最不经常使用（LFU）算法淘汰键。`allkeys-lfu` 会对所有键生效，而 `volatile-lfu` 只对设置了过期时间的键生效。

- **allkeys-random / volatile-random**  
  随机选择键进行淘汰。`allkeys-random` 会对所有键生效，而 `volatile-random` 只对设置了过期时间的键生效。

- **volatile-ttl**  
  优先淘汰那些剩余生存时间（TTL）较短的键。

如果选择了上述任意一种淘汰策略（除了 `noeviction`），即使内存被打满，Redis 仍然可以继续接受写入请求，但会根据策略自动淘汰旧的键以腾出空间。

---

### 2. **持久化与性能影响**
- 如果 Redis 启用了 RDB 或 AOF 持久化，在高写入压力下可能会导致持久化任务积压，进一步增加内存使用或引发性能问题。
- 在极端情况下，如果磁盘 I/O 无法跟上写入速度，可能会导致 Redis 响应变慢甚至挂起。

---

### 3. **解决方案建议**
如果 Redis 内存被打满且需要继续写入数据，可以考虑以下措施：

- **调整 maxmemory 和 maxmemory-policy**  
  根据业务需求选择合适的淘汰策略，例如 `allkeys-lru` 或 `volatile-lru`。

- **分片或集群部署**  
  将数据分散到多个 Redis 实例中，避免单个实例内存耗尽。

- **优化数据结构**  
  使用更紧凑的数据结构（如 Bitmap、HyperLogLog 等）减少内存占用。

- **设置过期时间**  
  对不再需要的键设置过期时间（`EXPIRE`），让 Redis 自动清理无用数据。

- **监控和报警**  
  使用监控工具（如 Prometheus + Grafana）实时跟踪 Redis 的内存使用情况，并设置合理的报警阈值。

---

### 总结
- 如果使用的是 `noeviction` 策略，内存打满后无法继续写入数据。
- 如果使用其他淘汰策略，Redis 会自动淘汰部分数据以腾出空间，允许继续写入。
- 推荐根据业务场景合理配置 `maxmemory` 和淘汰策略，同时结合分片、过期时间和监控手段优化 Redis 的使用。


 # redis 有一批key瞬间过期 为什么其他的key读写效率会变低？

当 Redis 中一批 key 瞬间过期时，可能会导致其他 key 的读写效率变低，原因可以归结为以下几个方面：

### 1. **Redis 内存回收机制**
- 当大量 key 同时过期时，Redis 需要立即释放这些 key 占用的内存。
- 如果内存中存在大量的过期 key（即使它们尚未被访问），Redis 会触发主动清理操作（`active expire`），这会导致 CPU 负载增加。
- 主动清理过程可能会占用主线程的时间，从而影响其他正常 key 的读写性能。

### 2. **主线程阻塞**
- Redis 是单线程处理命令的（除了部分 IO 操作和后台任务）。如果主线程花费较多时间处理过期 key 的清理工作，那么正常的读写请求会被延迟处理。
- 特别是在高并发场景下，这种延迟可能会被放大，导致整体性能下降。

### 3. **惰性删除的影响**
- Redis 使用的是**惰性删除**机制，即只有当客户端尝试访问一个已过期的 key 时，Redis 才会真正删除这个 key。
- 如果大量 key 同时过期但未被访问，Redis 可能会在后续的某个时间点集中清理这些 key，这也会导致短暂的性能波动。

### 4. **内存碎片化**
- 如果 Redis 使用的是非连续内存分配器（如 jemalloc 或 tcmalloc），大量 key 的同时删除可能会导致内存碎片化。
- 内存碎片化会影响 Redis 分配新内存的效率，从而间接降低读写性能。

### 5. **RDB/AOF 持久化压力**
- 如果启用了 RDB 或 AOF 持久化功能，大量 key 的同时过期可能会引发持久化文件的更新。
- 这种更新操作可能会占用额外的磁盘 IO 和 CPU 资源，进一步拖慢 Redis 的响应速度。

---

### 解决方案
针对上述问题，可以采取以下措施优化 Redis 性能：

1. **分散 key 的过期时间**
  - 避免大量 key 在同一时间过期。可以通过随机化过期时间（例如在目标时间基础上加一个小范围的随机值）来分散清理压力。

2. **调整 Redis 配置**
  - 增大 `hz` 参数（默认 10），以提高 Redis 检测和清理过期 key 的频率，减少单次清理的工作量。
  - 注意：增大 `hz` 会增加 CPU 使用率，需根据实际负载权衡。

3. **使用 Lua 脚本批量操作**
  - 如果需要批量删除 key，尽量使用 Lua 脚本分批执行，避免一次性删除过多 key。

4. **监控和调优**
  - 使用 Redis 自带的监控工具（如 `redis-cli --stat` 或第三方监控工具）观察内存使用、CPU 负载和延迟情况。
  - 根据监控数据调整配置或优化业务逻辑。

5. **升级硬件资源**
  - 如果 Redis 实例的 CPU 或内存资源不足，考虑升级硬件或扩展实例。

通过以上方法，可以有效缓解因大量 key 瞬间过期导致的性能问题。
