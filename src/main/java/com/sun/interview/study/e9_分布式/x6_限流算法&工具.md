# 计数器算法
- **原理**：在指定的时间窗口内，对请求进行计数。当请求数超过设定的阈值时，就对后续请求进行限流。例如，设定一分钟内允许的最大请求数为100，从0时刻开始计数，每来一个请求，计数器加1。如果在1分钟内计数器的值达到100，那么后续的请求就会被限流。
- **示例图**：
```
+---------+---------+---------+---------+---------+
| 时间窗口 |  0-10s  | 10-20s | 20-30s | 30-40s |
+---------+---------+---------+---------+---------+
| 请求数  |   20    |   30    |   30    |   20    |
+---------+---------+---------+---------+---------+
```
- **优缺点**：优点是实现简单，易于理解和部署。缺点是存在临界问题，比如在时间窗口切换时，如果在两个相邻的时间窗口边界处都有大量请求，可能会导致在短时间内实际处理的请求数超过阈值。
  漏桶算法
- **原理**：把请求想象成水，将水倒入一个漏桶中，漏桶以固定的速率出水，当桶满时，新的水会被溢出。在限流场景中，请求就像水一样流入漏桶，而漏桶按照固定的速率处理请求，如果请求过多，超过了漏桶的处理能力，多余的请求就会被丢弃。
- **示例图**
```
          +-------------------+
          |       漏桶        |
          |   +-----------+   |
          |   |  固定速率   |   |
          |   +-----------+   |
          |                   |
+-------->|                   |<--------+
|  请求  |                   |  处理后 |
|  流入  |                   |  请求  |
+-------->|                   |<--------+
          |                   |
          |   +-----------+   |
          |   |  丢弃请求   |   |
          |   +-----------+   |
          +-------------------+
```
- **优缺点**：优点是可以平滑请求，能很好地控制请求的处理速率，不会出现突发流量导致系统过载的情况。缺点是无法应对突发流量，即使系统在某一时刻有处理能力，也只能按照固定速率处理请求。

# 令牌桶算法
- **原理**：系统会以一个恒定的速率向一个令牌桶中放入令牌，每个请求在处理之前需要先从令牌桶中获取一个令牌，如果令牌桶中没有令牌，请求就会被阻塞或者拒绝。当令牌桶满时，新生成的令牌会被丢弃。由于令牌的生成速率是固定的，所以可以通过控制令牌的数量来限制请求的速率。
- **示例图**
```
          +-------------------+
          |     令牌桶       |
          |   +-----------+   |
          |   |  生成令牌   |   |
          |   +-----------+   |
          |   |  令牌数量   |   |
          |   +-----------+   |
          |                   |
+-------->|                   |<--------+
|  请求  |                   |  处理后 |
|  获取  |                   |  请求  |
|  令牌  |                   |        |
+-------->|                   |<--------+
          |                   |
          |   +-----------+   |
          |   |  无令牌时   |   |
          |   |  阻塞请求   |   |
          |   +-----------+   |
          +-------------------+
```
- **优缺点**：优点是能在限制请求速率的同时，允许一定程度的突发流量，只要令牌桶中有足够的令牌，就可以处理突发的请求。缺点是实现相对复杂一些，需要维护一个令牌桶的数据结构，并考虑令牌的生成和获取等操作。




固定窗口算法和滑动窗口算法是两种常用的流量控制算法，都可用于统计一段时间内的请求数量或流量信息，以实现限流等功能。以下是对它们的详细介绍：

# 固定窗口算法
- **原理**：将时间划分为固定长度的窗口，在每个窗口内统计请求数量或流量信息。当窗口内的请求数量达到设定的阈值时，就对后续的请求进行限流处理，比如拒绝请求或者让请求等待。
- **示例**：假设我们设定一个固定窗口为1分钟，限流阈值为100次请求。在第1分钟内，系统会统计收到的请求数量，如果达到了100次，那么在这1分钟内后续的请求就会被限流。当第2分钟开始时，又会重新在新的1分钟窗口内统计请求数量，不受上一分钟统计结果的影响。
- **优点**：实现简单，易于理解和部署。只需要在每个固定窗口开始时重置计数器，然后在窗口内累加请求数量，最后与阈值进行比较即可。
- **缺点**：存在临界问题。例如，在两个相邻的窗口边界处，如果请求量在第一个窗口的最后时刻突然激增，达到了限流阈值，而在第二个窗口开始时又有大量请求进来，由于窗口是独立统计的，这两个窗口内的请求都可能被允许，导致在实际的统计时间段内（两个窗口相加），请求量可能会超过预期的限流值的两倍，无法实现精确的限流控制。
#   滑动窗口算法
- **原理**：滑动窗口算法是对固定窗口算法的改进。它将时间划分为多个更小的时间片，每个时间片都有一个对应的计数器，窗口不再是固定的，而是随着时间的推移不断滑动。当有请求到来时，不仅要更新当前时间片的计数器，还要根据窗口的滑动规则，更新窗口内其他时间片的计数器，以准确统计当前窗口内的请求总数。当请求总数达到阈值时，进行限流操作。
- **示例**：假设我们将1分钟的时间划分为6个10秒的时间片，限流阈值为100次请求。随着时间的推移，窗口会不断滑动，每次滑动一个时间片。例如，从第1个10秒到第2个10秒，窗口就会向右滑动一个时间片，此时需要将第1个时间片的计数器的值累加到窗口的总计数器中，并减去即将滑出窗口的时间片（这里是第1个时间片）的计数器的值，然后再加上新进入窗口的时间片（这里是第2个时间片）的计数器的值，以此来实时更新窗口内的请求总数。
- **优点**：能够更精确地控制流量，避免了固定窗口算法在边界处的临界问题。因为窗口是连续滑动的，所以在任何时刻都能准确统计当前时间段内的请求数量，更符合实际的流量控制需求。
- **缺点**：实现相对复杂，需要维护多个时间片的计数器，并且在窗口滑动时需要进行较多的计算和数据更新操作。同时，由于需要记录更多的状态信息，对内存的消耗也相对较大。

下面用一个简单的图来表示两种算法的区别：

```
固定窗口算法：

+-----+-----+-----+
|     |     |     |
|  W1 |  W2 |  W3 |
|     |     |     |
+-----+-----+-----+

每个窗口独立统计请求数量，如W1内请求数达到阈值则在W1内限流，W2重新开始统计。

滑动窗口算法：

+-----+-----+-----+-----+-----+-----+
|  t1 |  t2 |  t3 |  t4 |  t5 |  t6 |
+-----+-----+-----+-----+-----+-----+

窗口不断滑动，例如从t1 - t6滑动到t2 - t7，实时更新窗口内请求总数。
```

综上所述，固定窗口算法简单但存在精度问题，适用于对限流精度要求不高的场景；滑动窗口算法能更精确地控制流量，但实现复杂，适用于对流量控制精度要求较高的场景，如金融交易系统、大型电商平台的促销活动等。
# sentinel中间件-限流

可以直接在Sentinel控制台配置限流规则，而不使用代码配置。使用`@SentinelResource`注解指定限流接口资源名称后，在Sentinel控制台配置规则时，只需确保规则中的资源名称与注解中指定的`value`值一致即可。

例如，有如下使用`@SentinelResource`注解的代码：
```java
@RestController
public class MyController {

    @GetMapping("/test")
    @SentinelResource(value = "myTestResource", blockHandler = "handleBlock")
    public String test() {
        return "正常处理业务逻辑";
    }

    // 限流处理方法
    public String handleBlock(BlockException ex) {
        return "请求被限流，请稍后再试！";
    }
}
```
在上述代码中，`@SentinelResource`注解的`value`属性指定了资源名称为`myTestResource`。此时，在Sentinel控制台配置限流规则时，将资源名称设置为`myTestResource`，并设置相应的限流条件（如QPS阈值等），即可对该接口进行限流。

这种方式实现了业务代码与限流配置的分离，方便在不修改代码的情况下，通过控制台灵活调整限流规则。
