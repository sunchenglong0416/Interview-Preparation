# 自动提交偏移量 默认

# consumer.properties
    bootstrap.servers=localhost:9092
    group.id=my-group
    key.deserializer=org.apache.kafka.common.serialization.StringDeserializer
    value.deserializer=org.apache.kafka.common.serialization.StringDeserializer
    enable.auto.commit=true
    auto.commit.interval.ms=5000  5s提交一次

## Kafka自动提交偏移量有以下缺点：
- **无法精确控制提交时机**：
        自动提交偏移量是按照固定的时间间隔进行的，无法根据消息处理的实际情况来准确提交偏移量。
        这就可能导致在一个时间间隔内，消费者已经处理了一部分消息，但还未到自动提交时间，
        此时若消费者发生故障重启，就会从上次提交的偏移量处重新消费，从而造成消息的重复消费。
- **可能导致数据不一致**：
        由于自动提交偏移量不依赖于消息处理的结果，若在消息处理过程中出现错误，而偏移量已经自动提交，那么就可能出现数据不一致的情况。
        例如，在将消息写入数据库时，如果消息处理失败但偏移量已提交，那么下次消费时就会跳过该消息，导致数据库中缺少相应的数据。
- **难以进行复杂的错误处理**：
        当自动提交偏移量出现问题时，例如网络故障导致提交失败，消费者很难进行复杂的错误处理。
        因为自动提交是由Kafka客户端自动完成的，开发者无法直接干预提交过程，也难以根据具体的错误情况采取相应的措施，如重试提交或进行补偿操作等。
- **无法适应特殊业务需求**：
      对于一些特殊的业务场景，如需要保证消息的严格顺序性、对消息的处理有严格的事务要求等，自动提交偏移量无法满足这些需求。
      因为自动提交无法精确控制偏移量的提交时机和条件，可能会破坏业务所要求的严格顺序或事务一致性。


# 手动同步提交偏移量（Manual Sync Commit Offset）

       定义： 消费者手动同步提交偏移量，确保偏移量提交成功后再继续处理下一批消息。
       配置参数：
       enable.auto.commit：禁用自动提交偏移量，默认为 false。
       适用的业务场景：
       数据一致性：适用于对数据一致性和准确性要求较高的场景。
       避免数据丢失：适用于需要确保数据不丢失的场景。
       优点：
       数据一致性：确保偏移量提交成功后再继续处理下一批消息，避免数据丢失。
       精确控制：精确控制偏移量提交的时间点。
       缺点：
       性能影响：每次提交偏移量都会阻塞消费者，可能影响性能。
       复杂性：需要显式地调用提交方法，增加开发复杂性。
   
# 手动异步提交偏移量（Manual Async Commit Offset）

    定义： 消费者手动异步提交偏移量，允许消费者在提交偏移量的同时继续处理下一批消息。
    配置参数：
    enable.auto.commit：禁用自动提交偏移量，默认为 false。
    适用的业务场景：
    高性能需求：适用于对性能要求较高的场景。
    避免阻塞：适用于需要避免阻塞消费者处理消息的场景。
    优点：
    高性能：异步提交偏移量，允许消费者在提交偏移量的同时继续处理消息。
    避免阻塞：避免同步提交偏移量带来的阻塞，提高消费性能。
    缺点：
    复杂性：需要显式地调用提交方法，并处理提交结果。
    数据丢失风险：如果异步提交失败且消费者继续处理消息，可能会导致数据丢失。


# 🫡同步提交也可能出现消息重复消费和消息丢失
Kafka使用手动同步提交时，仍然有可能出现重复消费或者消息丢失的情况，具体如下：
- **消息重复消费**
    - **提交失败导致重复消费**：在消息处理完成后，调用 `commitSync()` 方法提交偏移量时，如果出现网络问题、Kafka服务端异常等情况导致提交失败，而消费者没有正确处理这种情况，例如没有进行重试，那么当消费者重启或者重新分配分区时，就会从上次成功提交的偏移量之后开始消费，导致之前已经处理过但未成功提交偏移量的消息被重新消费。
    - **消费逻辑中的异常导致重复消费**：即使偏移量提交成功，但在消息处理逻辑中存在异常，导致消息实际上没有被正确处理或者处理结果没有被持久化。例如，在将消息写入数据库时，数据库操作出现部分失败，但偏移量已经提交，那么下次消费时，由于数据库中没有完整记录之前的处理结果，就会再次处理相同的消息。
- **消息丢失**
    - **提交后处理结果未持久化**：当 `commitSync()` 方法提交偏移量成功后，如果在消息处理结果的持久化过程中发生异常，例如数据库崩溃或者写入缓存未及时刷新到磁盘，而此时消费者进程被意外终止，那么下次重启消费者时，由于偏移量已经提交，就会跳过这些消息，导致消息丢失。
    - **消费者在提交前崩溃**：虽然手动同步提交可以在消息处理成功后再提交偏移量，但如果消费者在处理完消息但还未来得及调用 `commitSync()` 方法时就发生崩溃，那么这些已经处理过的消息的偏移量就不会被提交。当消费者重启后，就会再次消费这些消息，如果没有相应的幂等性处理机制，可能会导致数据不一致，从某种意义上说也属于消息丢失的一种情况（因为之前的处理结果丢失了）。

虽然手动同步提交偏移量能让开发者更精确地控制偏移量的提交时机，在一定程度上减少消息重复消费和丢失的可能性，但并不能完全杜绝这些问题。
开发者需要在代码中仔细处理各种异常情况，确保消息处理和偏移量提交的一致性和可靠性。
