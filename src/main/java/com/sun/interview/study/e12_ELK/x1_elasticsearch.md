以下是关于ES 7.0更详细的介绍：

### ES 7.0简介
Elasticsearch 7.0是一款开源的分布式、高扩展、高可用的搜索和数据分析引擎。它基于Lucene构建，能高效处理大规模的结构化和非结构化数据，提供近实时的搜索和分析功能，广泛应用于信息检索、日志分析、业务智能等领域。

### 核心组件
- **节点**：集群中的服务器，分为Master节点、Data节点、Coordinating节点等，承担不同角色和任务。
- **索引**：是具有相同结构的文档集合，类似数据库中的表。
- **分片**：索引可拆分为多个分片，分布在不同节点上，实现分布式存储和并行处理。
- **副本**：每个分片可以有多个副本，用于数据冗余和提高系统的可用性与查询性能。
- **Lucene**：底层的全文检索库，提供了强大的文本处理和索引功能。

### 索引字段类型选择
- **文本类型（text）**：用于存储大量文本数据，如文章内容、产品描述等，会进行分词处理以支持全文搜索。
- **关键字类型（keyword）**：适用于精确匹配的字段，如身份证号、邮政编码、标签等，不会分词，常用于过滤、排序和聚合操作。
- **数值类型（number）**：包括各种整数和浮点数类型，用于存储数值数据，方便进行数值计算和范围查询。
- **日期类型（date）**：用于存储日期和时间数据，支持多种日期格式，便于进行日期范围查询和时间序列分析。
- **布尔类型（boolean）**：存储布尔值，用于表示逻辑状态，如是否激活、是否删除等。
- **对象类型（object）**：用于存储复杂的嵌套数据结构，如包含多个属性的JSON对象。

### 最小高可用集群搭建对机器和内存的要求
- **机器要求**：建议采用至少3台服务器作为节点，以实现高可用性和数据冗余。服务器应具备稳定的网络连接、足够的磁盘空间和多核处理器，以支持ES的并发处理能力。
- **内存要求**：一般来说，每台服务器的内存配置应根据数据量和业务需求来确定。对于小型集群，每台服务器至少配备8GB内存；对于中型集群，16 - 32GB内存较为合适；对于大型集群，每台服务器可配置64GB及以上内存。同时，要为操作系统和其他必要进程预留一定的内存空间。

### 确定Master节点及Master节点挂了的处理方法
- **确定Master节点**：在ES集群中，节点启动时会通过分布式选举算法（如Zen Discovery）来选举Master节点。具有最高版本号的节点、具有最多集群状态信息的节点或符合特定选举规则（如节点ID顺序等）的节点会被选举为Master节点。Master节点负责管理集群的元数据，如索引的创建、删除，节点的加入、离开等。
- **Master节点挂了的处理**：当Master节点挂掉后，集群会自动触发重新选举流程。其他节点会根据选举算法重新选举出一个新的Master节点。在选举过程中，集群可能会短暂处于不稳定状态，部分操作可能会被阻塞，直到新的Master节点选举出来并恢复正常的集群管理。为了确保集群的高可用性，建议配置多个候选Master节点，以提高选举的成功率和集群的稳定性。

### 设置分片
- **考虑因素**：设置分片时需要综合考虑数据量、查询模式、集群规模和性能要求等因素。一般原则是，数据量越大，需要的分片越多，以实现数据的均匀分布和并行处理。同时，要避免分片过多导致管理成本过高和性能下降。
- **示例**：对于一个预计存储1TB数据的索引，假设平均每个分片可存储100GB数据，那么可以考虑设置10个主分片。如果集群有5台数据节点，每个节点可分配2个主分片。副本分片数量通常根据对数据可用性和查询性能的要求来设置，一般设置1 - 2个副本分片即可。

### 扩容及对性能的影响
- **扩容方法**：通过向集群中添加新的节点来实现扩容。新节点加入后，ES会自动进行数据重新分配和负载均衡，将部分分片从现有节点迁移到新节点上，以实现数据的均匀分布。
- **对性能的影响**：扩容过程中，由于数据迁移和集群状态的调整，可能会导致短期内系统性能下降，如查询响应时间变长、写入性能降低等。但扩容完成后，随着集群资源的增加，系统的整体性能和可扩展性会得到提升，能够处理更多的数据和更高的并发请求。


# 索引 分片路由逻辑
* 有文档ID
  * 根据文档ID 哈希计算 取余 主分片数  确定主分片 
  * 主分片确定后，协调节点会使用自适应副本选择（默认方式）来选择一个具体的分片副本进行查询
  * 在一些情况下，Elasticsearch 可能会优化查询流程，避免不必要的副分片查询。例如，如果主分片已经包含了足够的信息来满足查询需求，或者副分片的数据与主分片完全一致且没有发生变化，协调节点可能会只查询主分片，而不查询副分片，以提高查询性能。
* 无文档ID
  * 各个主分片的副本会单独查询，再汇总结果
# 分片和副本的职能
* 分片是索引的逻辑分组，是ES集群中存储数据的基本单位，基于分片可以实现数据的分布式存储和并行处理。
* 副本是主分片的备份，用于提高系统的可用性和查询性能。
# 分片和副本同步机制
    * 1.1 写操作流程
    客户端请求：客户端向 Elasticsearch 发送写请求（如索引、更新、删除）。
    路由：Elasticsearch 根据文档的 _id 字段进行哈希计算，确定文档所在的主分片。
    写入主分片：写请求被发送到主分片，主分片将数据写入其本地存储。
    写入副本分片：主分片将写请求同步到所有副本分片。同步可以通过以下几种方式实现：
    同步复制（Sync Replication）：默认情况下，Elasticsearch 使用同步复制机制。主分片在写入数据后，会等待所有副本分片确认收到数据，然后才认为写操作成功。
    异步复制（Async Replication）：在某些高级配置中，可以使用异步复制机制，但默认情况下不推荐使用。
    * 1.2 同步复制机制
    步骤：
    写入主分片：主分片将数据写入其本地存储。
    同步到副本分片：主分片将写请求同步到所有副本分片。
    确认写操作：主分片等待所有副本分片确认收到数据，然后才认为写操作成功。
# 默认分词器  中文分词器

Elasticsearch 7.0 的默认分词器是 `standard` 分词器。它支持中文，但对中文的分词效果不太理想，因为它主要是基于词的边界进行简单切分，对于中文这种没有明显词边界的语言，会将每个汉字作为一个单独的词进行处理。以下是一些ES中主流分词器及其优缺点：

    ### standard分词器
    - **优点**：是Elasticsearch默认的分词器，适用于多种语言，能对文本进行基本的标准化处理，如将文本转换为小写、去除标点符号等。在处理英文等有明确词边界的语言时，效果较好。
      - **缺点**：对中文分词效果差，不能准确识别中文词语，会导致分词结果过于细碎，不利于中文文本的检索和分析。
    
    ### ik分词器
    - **优点**：专门为中文设计，具有较高的中文分词准确性。它提供了两种分词模式，即 `ik_smart`（智能切分）和 `ik_max_word`（最大词长切分）。`ik_smart` 模式能将文本切分成比较符合语义的词语，`ik_max_word` 模式则会尽可能地将文本切分成多个词语，适用于不同的应用场景。同时支持自定义词典，可以根据业务需求添加特定的词汇，提高分词的准确性。
      - **缺点**：对于一些生僻词汇或新出现的词汇，可能无法准确分词。在处理大规模文本时，分词速度相对较慢。
    
    ### jieba分词器
    - **优点**：是一个流行的中文分词工具，在Python社区广泛应用。它具有良好的中文分词效果，能识别多种词性，支持多种分词模式，如精确模式、全模式和搜索引擎模式。可以通过加载用户自定义词典来提高分词的准确性，对于一些专业领域的词汇有较好的处理能力。
      - **缺点**：与Elasticsearch的集成相对复杂，需要进行额外的配置和开发工作。在处理一些复杂的中文句子或具有特殊语法结构的文本时，可能会出现分词错误的情况。
    
    ### HanLP分词器
    - **优点**：是一个功能强大的自然语言处理工具包，提供了多种分词算法和模型，具有较高的分词准确性和召回率。支持多种语言，除了中文外，还能处理英文、日文等多种语言的文本。具有丰富的语言知识和语义理解能力，能对文本进行词性标注、命名实体识别等多种自然语言处理任务。
      - **缺点**：对硬件资源的要求较高，在处理大规模文本时可能会占用较多的内存和CPU资源。与Elasticsearch的集成需要一定的技术成本，且运行速度相对一些轻量级的分词器较慢。


# 关键词查询执行过程

      1. **接收查询请求**：用户通过Elasticsearch提供的RESTful API发起关键词查询请求，请求通常是一个JSON格式的结构，包含查询条件、排序规则、分页参数等信息。
      2. **查询解析**：Elasticsearch解析查询请求，根据查询类型选择合适的查询引擎。查询使用DSL（Domain Specific Language）编写，DSL是基于JSON的查询语言，有丰富的查询方式，如 `match`、`term`、`range`、`bool` 等。
      3. **路由分片**：Elasticsearch是分布式的，数据分布在多个分片上。查询会经过路由过程，根据文档的某些属性（如文档的ID）决定在哪些分片上进行查询，确保每个查询请求只访问相关分片，提高效率。
      4. **查询执行**：查询请求被分发到具体的分片节点上，每个分片执行以下操作：
          - **倒排索引查找**：Elasticsearch根据查询的关键词在每个分片的倒排索引中查找相关文档。倒排索引记录了每个词出现在哪些文档中，能快速定位包含关键词的文档。
          - **评分计算**：使用TF - IDF（词频 - 逆文档频率）和BM25等算法计算每个文档的相关性分数（score），衡量文档与查询条件的匹配程度，分数越高越相关。
          - **过滤**：如果查询中有过滤条件（如范围查询、精确匹配等），Elasticsearch会根据过滤条件排除不符合的文档。
      5. **结果合并**：多个分片的查询结果被合并在一起，然后进行排序。排序通常按文档的相关性得分进行，得分高的文档排在前面。合并后的结果返回给协调节点，由协调节点整合成统一的响应。
      6. **结果排序和分页**：在合并查询结果后，Elasticsearch对结果进行排序，排序可基于相关性得分，也可基于其他字段。此外，可使用分页（`from`/`size`）限制返回的结果数量。
      7. **返回结果**：经过排序、过滤和分页后，最终的搜索结果以JSON格式返回给客户端，包含匹配的文档列表及相关元数据，如总匹配数、当前页码等信息。

# 索引模板
    在Elasticsearch 7.0中，索引模板具有以下重要作用：
    - **标准化索引结构**：通过索引模板，可以确保所有使用相同模板创建的索引具有一致的结构和配置。例如，在日志管理系统中，使用模板可以保证所有日志索引都有相同的字段定义、数据类型和分析器设置等，使得后续的查询和分析操作能够得到一致的结果。
    - **简化索引管理**：手动为每个新索引配置设置和映射是繁琐且易错的。而索引模板只需定义一次，就可自动应用于多个索引。如在时间序列数据场景中，像监控数据、传感器数据等，可能需要按一定时间间隔创建新索引，使用索引模板就能轻松实现，无需每次都重复设置索引的相关参数。
    - **提高数据处理效率**：模板可以指定索引的配置信息，如分片数、副本数、tranlog同步条件、refresh策略等，通过合理配置这些参数，能提高索引的性能和数据处理效率。例如，对于写入频繁的索引，适当调整refresh策略可以减少磁盘I/O操作，提高写入性能。
    - **实现数据隔离与多租户管理**：在多租户环境中，为每个租户定义一个模板，可以确保其数据按照特定的结构进行存储和索引，实现数据隔离。不同租户的数据可以通过各自的模板进行管理，保证数据的安全性和独立性。
    - **方便数据迁移和升级**：在进行数据迁移或Elasticsearch版本升级时，索引模板可以确保新索引与旧索引具有相同的结构。这样可以避免因索引结构不一致导致的数据丢失或查询错误等问题，使得数据迁移和升级过程更加平滑和稳定。

# 实时查询
    Elasticsearch 7.0默认情况下是支持实时查询的。
    在Elasticsearch中，文档一旦被索引，就可以立即被搜索到，这体现了它的近实时性（Near - Real - Time，NRT）特性。虽然从写入到可被查询会有轻微的延迟，但通常在秒级以内，对于大多数应用场景来说，可以认为是实时的。
    这一特性主要得益于Elasticsearch的索引结构和写入机制。它使用倒排索引来快速定位文档，并且在文档写入后会尽快将其刷新到内存中的索引缓存，使得新文档能够及时被查询到。同时，Elasticsearch也会定期将内存中的数据持久化到磁盘，以保证数据的可靠性和一致性。
# 快照查询
    

### 通过curl操作索引
- **创建索引**
```bash
curl -X PUT "http://localhost:9200/my_index" -H 'Content-Type: application/json' -d '
{
  "settings": {
    "number_of_shards": 3,
    "number_of_replicas": 1
  },
  "mappings": {
    "properties": {
      "field1": { "type": "text" },
      "field2": { "type": "keyword" },
      "field3": { "type": "integer" }
    }
  }
}'
```
- **查询索引**
```bash
curl -X GET "http://localhost:9200/my_index/_search?q=field1:value"
```
- **更新索引**
```bash
curl -X POST "http://localhost:9200/my_index/_update_by_query" -H 'Content-Type: application/json' -d '
{
  "query": {
    "match": {
      "field1": "old_value"
    }
  },
  "script": {
    "source": "ctx._source.field1 = \"new_value\""
  }
}'
```
- **分页查询索引**
```bash
curl -X GET "http://localhost:9200/my_index/_search?size=10&from=0"
```

### 索引ID选择
- **ES自动生成**：自动生成的索引ID具有唯一性和随机性，优点是方便快捷，避免了业务端生成ID可能出现的冲突和重复问题，适合对ID没有特定业务需求的场景。
- **外部业务指定**：外部业务指定的索引ID具有业务含义，便于根据业务逻辑进行数据关联和查询，但需要业务端保证ID的唯一性和正确性，增加了业务端的复杂性，适用于对ID有明确业务要求的场景。

### 分页快照查询与实时查询
- **分页快照查询**：使用scroll API实现分页快照查询。首先，发起一个带有scroll参数的初始查询，获取一个scroll_id：
```bash
curl -X POST "http://localhost:9200/my_index/_search?scroll=1m" -H 'Content-Type: application/json' -d '
{
  "query": {
    "match_all": {}
  },
  "size": 100
}'
```
然后，使用返回的scroll_id进行后续的分页查询：
```bash
curl -X POST "http://localhost:9200/_search/scroll" -H 'Content-Type: application/json' -d '
{
  "scroll": "1m",
  "scroll_id": "your_scroll_id"
}'
```
- **实时查询**：直接使用普通的查询语句进行实时查询，如：
```bash
curl -X GET "http://localhost:9200/my_index/_search?q=field1:value"
```
这种查询会实时返回当前索引中的数据，包括最新写入的数据。
