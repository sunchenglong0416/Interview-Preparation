# 分布式链路追踪系统
分布式链路追踪系统是一种用于在分布式系统中跟踪请求流程和性能的工具。它通过在各个服务节点上收集和记录请求的相关信息，
如请求的发起时间、经过的服务节点、处理时间等，将这些信息组合成一条完整的调用链，帮助开发人员快速定位问题、分析系统性能瓶颈。

### SkyWalking介绍
SkyWalking是一款开源的分布式链路追踪系统，具有强大的性能和丰富的功能。它采用了无侵入式的探针技术，能够自动收集应用程序的性能数据，支持多种语言和框架，
如Java、Python、.NET、Spring Cloud、Dubbo等。SkyWalking提供了直观的可视化界面，展示系统的拓扑结构、调用链路、性能指标等信息，方便用户快速了解系统的运行状态。

### SkyWalking核心组件
- **探针（Agent）**：负责收集应用程序的性能数据，包括请求的上下文信息、方法调用时间、数据库操作等。它通过字节码增强技术，在不修改应用程序代码的情况下，将追踪逻辑插入到应用程序中。
- **收集器（Collector）**：接收来自探针的性能数据，并对数据进行处理、分析和存储。收集器支持多种存储方式，如Elasticsearch、H2等，用户可以根据实际需求选择合适的存储方案。
- **存储（Storage）**：用于存储收集器处理后的数据，以便后续查询和分析。SkyWalking支持多种存储系统，不同的存储系统在性能、可扩展性和成本等方面有所不同。
- **可视化界面（UI）**：提供了直观的可视化界面，展示系统的拓扑结构、调用链路、性能指标等信息。用户可以通过UI快速定位问题、分析系统性能瓶颈。

### SkyWalking适用场景
- **分布式系统性能分析**：帮助开发人员快速定位系统中的性能瓶颈，分析各个服务节点的响应时间、吞吐量等指标，找出影响系统性能的关键因素。
- **故障排查**：在分布式系统中，当出现故障时，能够通过调用链快速定位问题所在的服务节点和具体的请求路径，缩短故障排查时间。
- **业务链路追踪**：对业务流程中的关键操作进行追踪，了解业务请求在各个服务之间的流转过程，确保业务流程的正确性和完整性。
- **系统优化**：根据收集到的性能数据，对系统进行优化，如调整服务的资源配置、优化数据库查询语句等，提高系统的整体性能。

### SkyWalking生成、传递、组合spanId形成调用链的方式
- **生成**：当请求进入应用程序时，SkyWalking的探针会为该请求生成一个唯一的`trace id`和一个`span id`。`span id`是一个64位的十六进制数字，由SkyWalking的内部算法生成，保证在整个分布式系统中是唯一的。每个`span`代表了请求在一个服务节点上的处理过程，包括方法调用、数据库操作等。
- **传递**：在服务之间进行调用时，SkyWalking会将`trace id`和`span id`通过请求的上下文进行传递。例如，在基于HTTP的微服务架构中，SkyWalking会将`trace id`和`span id`添加到HTTP请求的头信息中，随着请求一起传递到下游服务。当下游服务接收到请求时，会从请求头中提取`trace id`和`span id`，并将其作为当前请求的上下文信息。这样，`trace id`和`span id`就能够在整个分布式系统中传递，将各个服务节点上的`span`关联起来。
- **组合**：SkyWalking的收集器在接收到各个服务节点上报的`span`数据后，会根据`trace id`将属于同一请求的`span`组合成一条完整的调用链。收集器会按照`span`的父子关系和时间顺序，将各个`span`进行排序和组装，形成一个树形结构的调用链。在这个树形结构中，根节点是请求的入口点，叶子节点是请求的各个分支和子操作。通过这种方式，SkyWalking能够清晰地展示请求在分布式系统中的流转过程，帮助用户快速定位问题和分析性能瓶颈。
# SkyWalking收集和存储调用链日志主要通过以下几个关键步骤和组件来实现：

### 收集调用链日志
- **探针收集数据**：SkyWalking的Agent探针会在应用程序运行时，通过字节码增强等技术，自动拦截各种方法调用、数据库操作、网络请求等事件。针对每个被拦截的事件，
- 探针会创建一个`Span`对象来记录相关信息，包括`Span`的开始时间、结束时间、操作名称、关联的`Trace ID`和`Span ID`等。这些信息构成了调用链日志的基本数据。
- **数据上报**：Agent收集到`Span`数据后，会将其封装成特定的格式，通过网络发送给SkyWalking的收集器（Collector）。收集器通常会监听特定的端口，接收来自各个Agent的数据。

### 存储调用链日志
- **数据处理**：收集器接收到Agent上报的数据后，会对数据进行一系列的处理，包括数据解析、验证、聚合等操作。例如，将接收到的二进制数据解析为具体的`Span`对象，验证数据的合法性，并根据`Trace ID`将属于同一调用链的`Span`进行聚合。
- **存储到后端存储**：处理后的数据会被存储到指定的后端存储中。SkyWalking支持多种后端存储，如Elasticsearch、H2、MySQL等。以Elasticsearch为例，收集器会将`Span`数据转换为Elasticsearch可接受的格式，并通过HTTP请求将数据索引到Elasticsearch的相应索引中。在存储过程中，数据会按照一定的索引结构和字段映射进行存储，以便后续的查询和分析。例如，`Trace ID`、`Span ID`、服务名称、时间戳等信息会被存储为不同的字段，方便通过各种条件进行过滤和查询。

通过以上过程，SkyWalking能够有效地收集和存储分布式系统中的调用链日志，为后续的性能分析、故障排查等提供数据支持。

### SkyWalking 默认使用H2 数据库来存储日志 简化了部署过程，特别适合于开发环境和小型应用场景

### 高可用方案 ELK+SkyWalking

Elasticsearch、Filebeat、Kibana和SkyWalking可以通过以下方式配合完成日志收集和链路追踪：

### 日志收集
1. **SkyWalking配置日志输出**：在SkyWalking的配置文件`application.yml`中，将日志输出配置为文件形式。例如：
```yaml
logging:
  appender:
    console:
      target: SYSTEM_OUT
    file:
      name: ${SW_LOG_DIR:logs}/skywalking.log
```
这样SkyWalking会将相关日志记录到指定的文件中。
2. **Filebeat收集日志**：安装并配置Filebeat，在其配置文件`filebeat.yml`中指定要监控的SkyWalking日志文件路径。示例配置如下：
```yaml
filebeat.inputs:
- type: log
  enabled: true
  paths:
    - /var/log/skywalking/*.log
```
Filebeat会实时监控这些日志文件的变化，将新产生的日志收集起来。
3. **Filebeat发送日志到Elasticsearch**：在`filebeat.yml`中配置Elasticsearch输出，让Filebeat将收集到的日志发送到Elasticsearch中进行存储。配置示例：
```yaml
output.elasticsearch:
  hosts: ["localhost:9200"]
  index: "skywalking-logs-%{+YYYY.MM.dd}"
```

### 链路追踪
1. **SkyWalking链路数据收集**：SkyWalking本身具备强大的链路追踪功能，它会自动收集应用程序的链路数据，包括服务之间的调用关系、请求的流转路径、响应时间等信息。这些数据会以特定的格式存储在SkyWalking的存储中（如果之前配置了将数据存储到ES，那么就是存储在ES中）。
2. **Kibana可视化链路数据**：Kibana可以通过与Elasticsearch连接，读取SkyWalking存储在Elasticsearch中的链路数据，并进行可视化展示。用户可以在Kibana界面中通过各种图表、仪表盘等方式查看链路追踪的结果，例如查看服务之间的调用拓扑图、某个请求的详细链路轨迹、响应时间分布等。

通过以上配置和协作，Elasticsearch、Filebeat、Kibana和SkyWalking可以形成一个完整的日志收集和链路追踪系统，帮助用户更好地监控和分析应用程序的运行状态。在实际部署中，需要根据具体的业务需求和环境进行适当的调整和优化。


# SkyWalking采样率问题

在 SkyWalking 里，采样率指的是从所有请求中选取部分请求进行追踪的比例，借助调整采样率能够在性能开销与追踪效果之间取得平衡。以下为你介绍不同版本下修改采样率的位置和方式：

### 8.x 及以上版本
#### 基于 Agent 配置修改
- **配置文件路径**：在 SkyWalking Agent 的配置文件 `agent.config` 中修改采样率，此文件通常位于 Agent 目录下的 `config` 文件夹。
- **配置示例**：找到并修改 `agent.sample_n_per_3_secs` 参数。该参数代表每 3 秒内采样的请求数量，若设置为 `-1`，表示对所有请求进行采样；若设置为 `0`，则不进行采样；若设置为一个正整数 `n`，意味着每 3 秒内最多采样 `n` 个请求。
```properties
# 每3秒采样10个请求
agent.sample_n_per_3_secs=10
```
- **注意事项**：这种方式是在 Agent 端配置采样率，会对使用该 Agent 的应用程序生效。若要对不同应用程序设置不同的采样率，可分别为其配置不同的 Agent。

#### 基于 OAP 服务端配置修改（可选）
- **配置文件路径**：可以在 SkyWalking OAP（Observability Analysis Platform）服务端的 `application.yml` 配置文件里进行全局采样率的配置。该文件通常位于 OAP 服务端目录下的 `config` 文件夹。
- **配置示例**：找到 `trace` 部分并修改 `sampling` 参数。
```yaml
trace:
  sampling:
    # 采样率，范围从 0 到 1，这里表示采样率为 0.1，即 10% 的请求会被采样
    sample_rate: 0.1 
```
- **注意事项**：OAP 服务端的采样率配置是全局的，会影响所有接入该 OAP 服务端的应用程序。若同时在 Agent 端和 OAP 服务端都配置了采样率，Agent 端的配置优先级更高。

### 旧版本（7.x 及以下）
#### 基于 Agent 配置修改
同样是在 Agent 的配置文件中修改，不过参数名称可能有所不同，一般为 `agent.sample_rate`，其值是一个百分比，范围从 0 到 100。例如：
```properties
# 采样率为 20%
agent.sample_rate=20
``` 

* 修改完配置后，需要重启 SkyWalking Agent 或者 OAP 服务端，新的采样率配置才会生效。
