Redis最小高可用集群一般需要**6个节点**，采用3主3从的架构。这样的架构可以保证在有一个主节点出现故障时，集群仍然能够正常工作，因为每个主节点都有对应的从节点用于备份数据。

在Redis中，自动主从切换通常是通过哨兵（Sentinel）模式来实现的，其具体过程如下：
1. **主观下线**：哨兵会每秒向各个Redis节点发送PING命令来监测节点状态。如果在一定时间内（由 `down - after - milliseconds` 参数配置，默认30秒）没有收到某个主节点的回复，那么该哨兵会认为这个主节点主观下线，即单个哨兵认为主节点不可用。
2. **客观下线**：当一个哨兵认为主节点主观下线后，它会向其他哨兵发送 `is - master - down - by - addr` 指令询问该主节点是否真的挂了。当超过集群数量一半加1的哨兵都认为该主节点不可用时，就会达成共识，认为主节点客观下线，即多个哨兵都认定主节点不可用。
3. **选举哨兵领导者**：如果主节点被判定为客观下线，哨兵们会进行选举，选出一个哨兵领导者来执行故障转移操作。选举的方式是每个哨兵向其他哨兵发送“我要成为领导者”的命令，超过半数且大于 `quorum`（可在配置文件中设置）的哨兵同意后，该哨兵就会成为领导者。如果有多个哨兵同时成为领导者，则会在一段时间后再次进行选举。
4. **选择新主节点**：哨兵领导者从该主节点的从节点中选出一个合适的从节点作为新的主节点。选举的依据依次是：网络连接正常 -> 5秒内回复过 `INFO` 命令 -> 10 * `down - after - milliseconds` 内与主连接过的 -> 从服务器优先级 -> 复制偏移量 -> 运行ID较小的。
5. **执行故障转移**：哨兵领导者向选中的从节点发送 `slaveof no one` 命令，将其提升为新的主节点。然后向其他从节点发送命令，让它们成为新主节点的从节点。同时，更新原来的主节点配置为从节点，使其重新恢复去复制新主节点的信息。
6. **通知客户端**：哨兵通过发布订阅模式通知客户端新的主节点信息，客户端在收到通知后会自动连接到新的主节点进行数据交互。

# Redis集群模式 hash槽如何分配
### 1. 3 个节点时哈希槽的分配
在 Redis 集群模式下，默认有 16384 个哈希槽。当集群中有 3 个节点（假设为节点 A、节点 B 和节点 C）时，通常会尽可能均匀地分配这 16384 个哈希槽，大致分配情况如下：
- 节点 A：负责 0 - 5460 号哈希槽。
- 节点 B：负责 5461 - 10922 号哈希槽。
- 节点 C：负责 10923 - 16383 号哈希槽。
  这种分配方式是按照哈希槽编号顺序平均划分，使得每个节点管理的哈希槽数量大致相同，从而实现数据在各个节点上的相对均匀分布。
### 2. 增加或减少节点时对集群的影响及再分配方式
#### 增加节点
- **影响**：增加节点时，需要将部分哈希槽从现有的节点迁移到新节点上，以实现负载均衡。在迁移过程中，可能会对集群的读写性能产生一定影响，因为需要在节点之间进行数据的复制和移动。但 Redis 集群支持在线迁移哈希槽，不会导致整个集群下线。
- **再分配方式**：
    1. **手动迁移**：使用 `CLUSTER SETSLOT` 等相关命令手动指定要迁移的哈希槽以及目标节点。例如，要将节点 A 的部分哈希槽迁移到新节点 D，可以先计算出需要迁移的哈希槽范围，然后依次执行迁移命令。
    2. **自动平衡**：可以使用 Redis 集群管理工具（如 `redis-trib.rb` 或 Redis Cluster Manager）来自动进行哈希槽的重新分配。这些工具会根据集群的当前状态，自动计算出如何将哈希槽从现有节点迁移到新节点，以达到负载均衡的目的。
#### 减少节点
- **影响**：减少节点时，需要将该节点负责的哈希槽迁移到其他节点上。在迁移过程中，同样会对集群的性能产生一定影响。如果该节点存储了大量的数据，迁移过程可能会比较耗时。
- **再分配方式**：
    1. **手动迁移**：先将待移除节点的所有哈希槽迁移到其他节点上，然后使用 `CLUSTER FORGET` 命令将该节点从集群中移除。
    2. **自动平衡**：使用集群管理工具自动将待移除节点的哈希槽迁移到其他节点，并完成节点的移除操作。
### 3. Redis 采用 CRC16 算法并建议使用 16384 个槽位的原因
#### 减少网络带宽消耗
在 Redis 集群中，节点之间会通过发送心跳包来交换集群状态信息，其中包括每个节点负责的哈希槽信息。每个哈希槽的状态信息使用位图表示，若采用 16384 个槽位，状态信息需占用 2KB 空间；而若采用 CRC16 算法可产生的最大 65536 个槽位，则需 8KB 空间。由于 Redis 每秒会发送多个心跳包，8KB 的消息头过大，会浪费网络带宽。使用 16384 个槽位可以在保证信息完整性的同时，减少网络带宽的消耗。
#### 适合大多数集群规模
Redis 集群的节点个数通常不会超过 1000 个，因为节点过多会使心跳包携带的数据量过大，导致网络拥堵。对于节点数在 1000 以内的集群，16384 个槽位足以保证数据均匀分布，每个节点平均可管理约 16 个槽位，避免了单个节点管理过多或过少槽位的情况。
#### 提高压缩率和传输效率
Redis 主节点的哈希槽信息通过 bitmap 存储，传输时会进行压缩。槽位数量越少，bitmap 填充率越低，压缩率越高。16384 个槽位在保证数据分片粒度的同时，能使 bitmap 在大多数情况下保持较低的填充率，提高压缩率和传输效率。
#### 位运算效率高
16384 是 2 的幂次方，这对于计算机进行位运算非常友好，能高效地进行取模运算，快速确定键所属的槽位，在性能和资源消耗之间取得良好的平衡。同时，这个数量也能在大多数应用场景中提供足够的分片粒度，保持集群管理和配置的简单性。



# 一致性hash

一致性哈希是一种分布式系统中常用的哈希算法，用于将数据均匀地分布在多个节点上，同时在节点增加或减少时，尽可能减少数据的迁移。以下是其介绍及解决方案：

### 一致性哈希介绍
- **基本原理**：一致性哈希将整个哈希值空间组织成一个虚拟的圆环，称为哈希环。哈希环的范围是从0到 $2^{32}-1$，数据和节点都通过哈希函数映射到这个环上。当有数据需要存储或查找时，先计算数据的哈希值，然后在哈希环上顺时针查找第一个大于等于该哈希值的节点，这个节点就是存储或查找数据的目标节点。
- **优点**
  - **节点增减时数据迁移少**：当增加或减少节点时，只有该节点附近的一小部分数据需要迁移，而不是像传统哈希算法那样，可能导致大量数据在不同节点之间重新分配。
  - **数据分布均匀**：在理想情况下，数据能够均匀地分布在各个节点上，避免出现数据倾斜的情况，即某些节点存储的数据量远远多于其他节点。
- **缺点**
  - **存在数据热点**：如果节点数量较少，可能会出现某些节点对应的哈希环区间较大，导致这些节点承担的负载较重，形成数据热点。
  - **实现复杂**：相比传统的哈希算法，一致性哈希的实现相对复杂，需要考虑哈希环的维护、节点的加入和退出等问题。

### 一致性哈希解决方案
- **虚拟节点**：为了解决数据热点问题，可以引入虚拟节点的概念。每个实际节点对应多个虚拟节点，这些虚拟节点均匀地分布在哈希环上。数据先映射到虚拟节点，再由虚拟节点映射到实际节点。这样可以增加节点在哈希环上的分布密度，使数据更加均匀地分布在各个实际节点上，避免数据热点的出现。
- **哈希函数选择**：选择合适的哈希函数对于一致性哈希的性能至关重要。好的哈希函数应该具有良好的散列性，能够将数据均匀地分布在哈希环上，并且具有较低的冲突率。常见的哈希函数如MD5、SHA-1等都可以用于一致性哈希，但在实际应用中，需要根据具体情况进行选择和优化。
- **节点管理**：需要设计合理的节点加入和退出机制。当新节点加入时，要将其对应的虚拟节点均匀地插入到哈希环中，并重新分配相关数据；当节点退出时，要将其负责的数据迁移到其他节点上，并更新哈希环的状态。同时，还需要考虑节点故障的情况，及时检测到故障节点并进行相应的处理，以保证系统的可用性和数据的完整性。
- **负载均衡**：结合负载均衡算法，根据节点的负载情况动态调整数据的分布。例如，可以定期监测各个节点的负载指标，如CPU使用率、内存使用率、网络带宽等，当发现某个节点负载过高时，将其部分数据迁移到负载较低的节点上，以实现系统的负载均衡。

# redis集群模式 主从自动切换过程

在 Redis 集群模式中，**主从自动切换（故障转移）** 是集群实现高可用的重要机制之一。Redis 集群本身不依赖哨兵（Sentinel），而是通过 **集群节点间的内部通信与协调机制** 来完成主从切换。

以下是 Redis 集群模式下主从自动切换的完整过程：

---

## 🔁 一、主从切换触发条件

1. **主节点宕机或网络中断**
  - 主节点无法响应其他节点的心跳请求；
  - 超过集群配置的最大容忍时间（`node timeout`）未恢复。

2. **超过半数主节点确认该主节点下线**
  - 其他主节点在 `node timeout` 时间内多次尝试连接失败后，会标记该节点为 **PFAIL（Possible Fail）**；
  - 当集群中大多数主节点都确认这个节点不可达时，状态升级为 **FAIL（实际下线）**。

---

## 🧠 二、主从切换流程详解

### 1. **发现主节点下线**
- 每个节点每隔一段时间发送 PING 消息给其他节点；
- 如果某个节点长时间未收到某主节点的 PONG 响应，标记其为 **PFAIL（主观下线）**；
- 然后通过 Gossip 协议广播这一信息。

### 2. **达成客观下线共识（FAIL）**
- 当其他节点收到 PFAIL 通知后，也会检查自己是否也收不到该主节点的响应；
- 如果超过集群半数以上的主节点都认为该节点下线，则将其标记为 **FAIL（客观下线）**。

### 3. **选举新的主节点**
- 由该主节点的从节点发起选举，争夺成为新主。
- 选举规则包括：
  - 优先选择数据最接近原主节点的从节点（复制偏移量最大）；
  - 若多个从节点偏移量相同，则选择运行 ID 更小的节点。

### 4. **投票与仲裁**
- 每个主节点会对候选从节点进行投票；
- 候选从节点需要获得集群中大多数主节点的投票才能成功晋升为主节点。

### 5. **执行故障转移**
- 成功当选的新主节点将自己的角色更改为主，并开始接受客户端写请求；
- 其他从节点将自己设置为新主节点的从节点，开始同步数据；
- 原主节点恢复后，如果发现自己已经被替代，会自动降级为从节点并同步新主节点的数据。

### 6. **更新集群拓扑信息**
- 新的主节点信息通过 Gossip 协议广播到整个集群；
- 所有节点更新自己的路由表和槽位映射关系；
- 客户端在下次请求时也会自动重定向到新的主节点。

---

## 📌 三、关键参数说明

| 参数 | 默认值 | 含义 |
|------|--------|------|
| `cluster-node-timeout` | 15s | 判断节点是否下线的时间阈值 |
| `cluster-replica-validity-factor` | 10 | 控制从节点是否有资格参与选举（影响数据新鲜度判断） |
| `cluster-migration-barrier` | 1 | 表示一个从节点必须至少连接多少个主节点才会被允许迁移 |

---

## ✅ 四、总结

Redis 集群的主从自动切换是完全去中心化的，依靠节点之间的通信和投票机制实现，无需额外部署哨兵。其核心步骤如下：

1. 主观下线 →
2. 客观下线（多数确认）→
3. 从节点选举 →
4. 投票仲裁 →
5. 故障转移 →
6. 拓扑更新

这种机制保证了 Redis 集群在主节点故障时能够快速恢复服务，提升系统的高可用性。
